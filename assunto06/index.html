📨 DTOs (Data Transfer Objects) Aula 11 Revisão

🔹 É um POJO (classe Java simples);
🔹 NÃO é uma entidade (não tem @Entity);
🔹 É um "contêiner" de dados feito sob medida para sua API;
🔹 Você define exatamente quais campos o cliente pode ver e quais pode enviar;
🔹 Contrato da API: seu DTO;
🔹 Persistência: sua Entidade.

Entidade (Banco) vs. DTO (API), com o Usuario do Task Manager:

// Usuario.java (@Entity) @Entity public class Usuario { @Id private Long id; private String nome; private String email; private String senha; // Sensível private List<Tarefa> tarefas; // Interno } // UsuarioDTO.java (POJO) public class UsuarioDTO { private Long id; private String nome; private String email; // Sem senha! // Sem tarefas }

🔹 O TarefaDTO da aula 10 segue igual nesta aula: id, titulo, descricao, prioridade, prazo, concluida, usuarioId, com as validações (@NotBlank, @Size, @NotNull). O que muda é quem converte e onde a conversão acontece.

✍ Mapeamento Manual e Automático Aula 11 set... set... set...

Mapeamento Manual: escrevemos o código de conversão na mão. É o que o UsuarioController faz desde a aula 10:

private UsuarioDTO converterParaDto(Usuario usuario) { UsuarioDTO dto = new UsuarioDTO(); dto.setId(usuario.getId()); dto.setNome(usuario.getNome()); dto.setEmail(usuario.getEmail()); return dto; }

🔹 Usamos uma biblioteca para fazer o trabalho pesado.
🔹 Princípio: ele "lê" os nomes dos atributos e copia os valores se os nomes forem iguais (nome -> nome).
🔹 Dependência (pom.xml):

⚙ Configurando e Usando o ModelMapper Aula 11 Obrigatório!

🔹 Configurando o ModelMapper (Obrigatório!). Precisamos "ensinar" o Spring a criar e gerenciar o ModelMapper. Criamos uma classe de configuração com a anotação @Bean:

package br.org.irede.taskmanagerapi.config; import org.modelmapper.ModelMapper; import org.springframework.context.annotation.Bean; import org.springframework.context.annotation.Configuration; @Configuration public class AppConfig { @Bean public ModelMapper modelMapper() { return new ModelMapper(); } }

🔹 Usando o ModelMapper (é simples!). Injetamos o ModelMapper em nossa classe de serviço e usamos o método .map(). O código do slide, com o Usuario:

@Autowired private ModelMapper modelMapper; // Injeta o bean @Autowired private UsuarioRepository repository; public UsuarioDTO buscarPorId(Long id) { Usuario usuario = repository.findById(id).orElseThrow(); // Mapeamento automático! return modelMapper.map(usuario, UsuarioDTO.class); }

🔹 No Task Manager, injetamos pelo construtor, como já fazemos nos controladores desde a aula 07, e trocamos o orElseThrow() vazio pela ResourceNotFoundException da aula 09 (senão o id 99 vira 500):

package br.org.irede.taskmanagerapi.service; @Service public class UsuarioService { private final UsuarioRepository repository; private final ModelMapper modelMapper; public UsuarioService(UsuarioRepository repository, ModelMapper modelMapper) { this.repository = repository; this.modelMapper = modelMapper; } public UsuarioDTO buscarPorId(Long id) { return modelMapper.map(buscarUsuario(id), UsuarioDTO.class); } // Usado pelo TarefaService: toda tarefa precisa de um dono que exista public Usuario buscarUsuario(Long id) { return repository.findById(id) .orElseThrow(() -> new ResourceNotFoundException("Usuário com id " + id + " não encontrado")); } }
⚠ ModelMapper na saída, cópia explícita na entrada. No sentido entidade → DTO ele é perfeito. No sentido contrário, modelMapper.map(dto, Tarefa.class) copia tudo o que tiver nome compatível: o id que o cliente mandar no JSON vai para a entidade, e o usuarioId vira um new Usuario() com aquele id dentro de tarefa.usuario. Por isso, no TarefaService, os dados de entrada são copiados campo a campo, e o id e o dono ficam sob controle do service.
🏛 Integração com Banco de Dados via JPA: a Camada de Serviço Aula 11 3 camadas

Agora que temos DTOs e uma forma de mapeá-los, onde essa conversão deve acontecer? A resposta é: na Camada de Serviço (Service Layer). A arquitetura padrão de uma API Spring Boot é dividida em três camadas:

AnotaçãoCamadaNo Task Manager
@RestControllerApresentaçãoTarefaController: rota, status HTTP, @Valid
@ServiceServiço / NegócioTarefaService: regra do dono, 404, conversão
@RepositoryAcesso a DadosTarefaRepository: JPA e SQL

Prática: CRUD Completo com DTOs e Serviços. O TarefaService da aula 11 recebe tudo o que o controlador fazia:

package br.org.irede.taskmanagerapi.service; @Service public class TarefaService { private final TarefaRepository repository; private final UsuarioService usuarioService; private final ModelMapper modelMapper; public TarefaService(TarefaRepository repository, UsuarioService usuarioService, ModelMapper modelMapper) { this.repository = repository; this.usuarioService = usuarioService; this.modelMapper = modelMapper; } public List<TarefaDTO> listar() { return repository.findAll().stream() .map(this::converterParaDto) .toList(); } public TarefaDTO buscarPorId(Long id) { return converterParaDto(buscarTarefa(id)); } public TarefaDTO criar(TarefaDTO dto) { Usuario dono = usuarioService.buscarUsuario(dto.getUsuarioId()); // 404 se não existir Tarefa tarefa = new Tarefa(); copiarParaEntidade(dto, tarefa); tarefa.setUsuario(dono); return converterParaDto(repository.save(tarefa)); } public TarefaDTO atualizar(Long id, TarefaDTO dto) { Tarefa tarefa = buscarTarefa(id); copiarParaEntidade(dto, tarefa); // o dono não muda no PUT return converterParaDto(repository.save(tarefa)); } public void remover(Long id) { if (!repository.existsById(id)) { throw new ResourceNotFoundException("Tarefa com id " + id + " não encontrada"); } repository.deleteById(id); } private Tarefa buscarTarefa(Long id) { return repository.findById(id) .orElseThrow(() -> new ResourceNotFoundException("Tarefa com id " + id + " não encontrada")); } // Saída: Entity → DTO (Mapeamento automático!) private TarefaDTO converterParaDto(Tarefa tarefa) { return modelMapper.map(tarefa, TarefaDTO.class); } // Entrada: DTO → Entity (o id e o dono nunca vêm do cliente) private void copiarParaEntidade(TarefaDTO dto, Tarefa tarefa) { tarefa.setTitulo(dto.getTitulo()); tarefa.setDescricao(dto.getDescricao()); tarefa.setPrioridade(dto.getPrioridade()); tarefa.setPrazo(dto.getPrazo()); tarefa.setConcluida(dto.isConcluida()); } }

🔹 O service não conhece HTTP: não há ResponseEntity, status nem URI nele. Ele lança ResourceNotFoundException, e o GlobalExceptionHandler da aula 09 continua traduzindo para 404, porque a exceção sobe pelo controlador do mesmo jeito.

🔹 O TarefaService usa o UsuarioService (não o UsuarioRepository) para achar o dono: a regra "usuário inexistente → 404" fica escrita em um lugar só.

🧱 Boas Práticas de Arquitetura e Separação de Camadas Aula 11

Um projeto profissional é organizado por responsabilidade.

br.org.irede.taskmanagerapi/ ├── controller/ (APIs, HTTP) ├── service/ (Lógica de Negócio) ├── repository/ (Acesso ao Banco) ├── model/ (Entidades @Entity) ├── dto/ (Classes de Transferência) └── config/ (Beans, Segurança)

Pense na sua Camada de Serviço como o núcleo protegido da sua aplicação:

Fluxo de Entrada (POST): JSON → Controller → TarefaDTO (Validado) → Fronteira (Service) → Tarefa (Entity) → Repository → Banco Fluxo de Saída (GET): Banco → Repository → Tarefa (Entity) → Fronteira (Service) → TarefaDTO → Controller → JSON

🔹 O Controlador e o Cliente Externo nunca tocam na Entidade. Com o service, isso passa a ser verdade no Task Manager: o controlador não importa mais nada de model nem de repository.

@RestController @RequestMapping("/api/v1/tarefas") public class TarefaController { private final TarefaService service; public TarefaController(TarefaService service) { this.service = service; } @GetMapping public List<TarefaDTO> listar() { return service.listar(); } @GetMapping("/{id}") public TarefaDTO buscarPorId(@PathVariable Long id) { return service.buscarPorId(id); } @PostMapping public ResponseEntity<TarefaDTO> criar(@Valid @RequestBody TarefaDTO dto) { TarefaDTO criada = service.criar(dto); URI location = URI.create("/api/v1/tarefas/" + criada.getId()); // aula 12 melhora return ResponseEntity.created(location).body(criada); } @PutMapping("/{id}") public TarefaDTO atualizar(@PathVariable Long id, @Valid @RequestBody TarefaDTO dto) { return service.atualizar(id, dto); } @DeleteMapping("/{id}") public ResponseEntity<Void> remover(@PathVariable Long id) { service.remover(id); return ResponseEntity.noContent().build(); } }
📌 Repare no que não mudou: as rotas, os status e o JSON são os mesmos da aula 10. A coleção do Postman passa inteira sem alteração. Refatorar camadas é mexer por dentro sem quebrar o contrato.
🌐 Lembram o que é REST? Princípios 1 a 3 Aula 12 Estilo arquitetural

🔹 REpresentational State Transfer.
🔹 Não é um protocolo, não é uma ferramenta.
🔹 É um ESTILO ARQUITETURAL (um conjunto de regras/restrições).
🔹 Definido por Roy Fielding (co-fundador do HTTP).
🔹 Objetivo: criar sistemas em hipermídia (como a Web) que sejam escaláveis, confiáveis e fáceis de manter.

Uma API é RESTful quando respeita essas restrições. As quatro do slide:

Princípio 1: Cliente-Servidor. Separação de responsabilidades:

LadoFocoNo Task Manager
Cliente (Frontend)Interface e Experiência do Usuário (UI/UX)Postman hoje; um app web ou mobile amanhã
Servidor (Backend)Lógica de Negócio e Persistência de DadosSpring Boot + PostgreSQL

🔹 Vantagem: podem evoluir de forma independente. O contrato entre os dois são as rotas e os DTOs.

Princípio 2: Stateless (Sem Estado). O servidor NÃO armazena o estado do cliente (sessão). O servidor "esquece" do cliente após cada resposta. Toda requisição deve conter toda a informação necessária para ser processada (ex.: token de autenticação JWT).

// Errado (Stateful): o servidor guarda quem está logado Usuario logado = (Usuario) session.getAttribute("usuarioLogado"); // Correto (Stateless): cada requisição se identifica sozinha GET /api/v1/tarefas Authorization: Bearer <token>

🔹 Vantagem: alta escalabilidade (qualquer servidor pode responder). No Task Manager, o JWT e o SessionCreationPolicy.STATELESS chegam nas aulas 13 e 14.

Princípio 3: Cacheable. As respostas do servidor devem se autodefinir como "cacheáveis" ou "não-cacheáveis". Exemplo: o servidor responde a um GET /produtos com o cabeçalho Cache-Control: max-age=300 (cache por 5 minutos). O cliente ou um proxy pode armazenar essa resposta.

// Como o Spring escreve esse cabeçalho (exemplo, não entra no projeto) return ResponseEntity.ok() .cacheControl(CacheControl.maxAge(5, TimeUnit.MINUTES)) // Cache-Control: max-age=300 .body(dto);

🔹 Vantagem: performance. Reduz a carga no servidor.

🧭 Princípio 4: Interface Uniforme Aula 12

🔹 Identificação de Recursos (URIs): usar substantivos, não verbos. O verbo já está no método HTTP.

SlideNo Task Manager
GET /clientes/1GET /api/v1/tarefas/1✅ Bom
GET /buscarClientePorId?id=1GET /api/v1/buscarTarefaPorId?id=1❌ Ruim

🔹 Manipulação via Representações: o cliente manipula um JSON, não o dado no banco. No Task Manager, essa representação é o TarefaDTO, e quem chega na linha da tabela é só o service.

🔹 Mensagens Autodescritivas: cabeçalhos como Content-Type: application/json (o que estou enviando) e Accept: application/json (o que aceito receber). O Postman envia os dois quando o corpo é raw → JSON.

🔹 HATEOAS: respostas contêm links para as próximas ações possíveis. Uma ideia do formato (não implementado no Task Manager):

{ "id": 1, "titulo": "Estudar JPA", "_links": { "self": { "href": "http://localhost:8080/api/v1/tarefas/1" }, "usuario": { "href": "http://localhost:8080/api/v1/usuarios/1" } } }
🔧 Verbos HTTP Principais (CRUD) e PUT vs. PATCH Aula 12 PATCH no projeto
VerboOperaçãoSemânticaIdempotente?Seguro?
GETReadBusca um recurso ou uma coleção.SimSim
POSTCreateCria um novo recurso.NãoNão
PUTUpdateSubstitui totalmente um recurso existente.SimNão
DELETEDeleteRemove um recurso.SimNão

🔹 Seguro: não altera nada no servidor. Idempotente: repetir a mesma requisição deixa o servidor no mesmo estado que uma vez só. Dois POST /tarefas iguais criam as tarefas 9 e 10; dois PUT /tarefas/1 iguais deixam a tarefa 1 igual.

PUT vs. PATCH: ambos atualizam, mas de formas diferentes.

PUT = Substituição TotalPATCH = Atualização Parcial
SlidePUT /usuarios/1 com {"nome": "Ana"}: o usuário 1 agora só tem nome; o email e o telefone são apagados (null).PATCH /usuarios/1 com {"nome": "Ana"}: o nome é atualizado para "Ana"; o email e o telefone são mantidos.
Task ManagerPUT /tarefas/1: o que não vier no corpo vira null (descrição, prazo) ou o padrão (concluida = false). Campos obrigatórios ausentes → 400.PATCH /tarefas/1 com {"concluida": true}: só a conclusão muda, o resto fica.

O PATCH no Task Manager: o service só copia o que veio preenchido. Para isso, TarefaDTO.concluida passa de boolean para Boolean: com o primitivo, "não veio no JSON" e "veio false" seriam a mesma coisa.

// TarefaDTO.java (aula 12) private Boolean concluida; // era boolean: null agora significa "não informado" // TarefaController.java @PatchMapping("/{id}") public TarefaDTO atualizarParcial(@PathVariable Long id, @RequestBody TarefaDTO dto) { return service.atualizarParcial(id, dto); // sem @Valid: no PATCH, quase tudo é opcional } // TarefaService.java public TarefaDTO atualizarParcial(Long id, TarefaDTO dto) { Tarefa tarefa = buscarTarefa(id); if (dto.getTitulo() != null) tarefa.setTitulo(dto.getTitulo()); if (dto.getDescricao() != null) tarefa.setDescricao(dto.getDescricao()); if (dto.getPrioridade() != null) tarefa.setPrioridade(dto.getPrioridade()); if (dto.getPrazo() != null) tarefa.setPrazo(dto.getPrazo()); if (dto.getConcluida() != null) tarefa.setConcluida(dto.getConcluida()); return converterParaDto(repository.save(tarefa)); } // e no copiarParaEntidade do PUT: ausente = false (substituição total) tarefa.setConcluida(Boolean.TRUE.equals(dto.getConcluida()));
⚠ tarefa.setConcluida(dto.getConcluida()) no PUT daria NullPointerException quando o campo não viesse: o setter da entidade recebe boolean, e o Java tenta desembrulhar o null. O Boolean.TRUE.equals(...) resolve: null e false viram false.
📛 Convenções RESTful: Plural e Hierarquia Aula 12 sub-recurso no projeto

Convenção 1: Substantivos no Plural. Por quê? A rota representa a coleção de recursos.

🔹 /clientes = a coleção de clientes.  🔹 /clientes/1 = o item 1 da coleção de clientes.

Ruim (Singular)Bom (Plural)No Task Manager
/cliente/clientes/api/v1/tarefas, /api/v1/usuarios
/cliente/{id}/clientes/{id}/api/v1/tarefas/{id}

Convenção 2: Hierarquia (Sub-recursos). Quando um recurso pertence a outro, a URI deve mostrar isso.

CenárioSlideNo Task Manager
Buscar os pedidos do cliente 123 — abordagem OK (filtro)GET /pedidos?clienteId=123GET /tarefas?usuarioId=2
Buscar os pedidos do cliente 123 — abordagem RESTful (hierarquia)GET /clientes/123/pedidosGET /usuarios/2/tarefas
Criar um novo pedido para o cliente 123 — abordagem RESTfulPOST /clientes/123/pedidosPOST /usuarios/2/tarefas (alternativa)

No projeto, a aula 12 cria o GET hierárquico no UsuarioController. O POST continua em /tarefas com usuarioId no corpo, para não quebrar a coleção: as duas formas são aceitas pelo slide.

// UsuarioController.java (aula 12) @GetMapping("/{id}/tarefas") public List<TarefaDTO> listarTarefas(@PathVariable Long id) { return tarefaService.listarPorUsuario(id); } // TarefaService.java — reaproveita a @Query da aula 05 public List<TarefaDTO> listarPorUsuario(Long usuarioId) { usuarioService.buscarUsuario(usuarioId); // usuário 99 → 404, não lista vazia return repository.findByUsuarioId(usuarioId).stream() .map(this::converterParaDto) .toList(); }

🔹 Por que 404 e não []? /usuarios/99/tarefas é um sub-recurso de /usuarios/99: se o pai não existe, o filho também não. Já /usuarios/3/tarefas de um usuário sem tarefas responderia 200 [].

🔖 Versionamento de APIs Aula 12 Breaking change

O problema: mudanças quebram o contrato.

🔹 Sua API é um contrato com seus clientes (apps mobile, web).
🔹 Se você lança a v1 e um app mobile a utiliza, você não pode simplesmente mudar a resposta!
🔹 Breaking Change: remover ou renomear um campo JSON.

// v1 retorna: { "nomeCompleto": "Ana Silva" } // v2 retorna: { "nome": "Ana", "sobrenome": "Silva" }

🔹 O app mobile (v1) que espera nomeCompleto vai quebrar.
🔹 Solução: manter a v1 funcionando e lançar a v2 em paralelo.

Abordagem 1: na URI (Comum)Abordagem 2: no Cabeçalho
ComoA versão faz parte da URL.
GET /api/v1/produtos
GET /api/v2/produtos		A URI permanece limpa. A versão é pedida em um cabeçalho.
GET /api/produtos + X-API-VERSION: 1
GET /api/produtos + X-API-VERSION: 2
PrósMuito claro e explícito. Fácil de testar (só mudar a URL). Fácil de implementar no Spring (@RequestMapping("/api/v1")).A URI do recurso é perpétua.
Contras"Polui" a URI.Mais difícil de testar (não dá para fazer no navegador). Menos explícito para quem está consumindo.
// Abordagem 1 — a do Task Manager desde a aula 07 @RestController @RequestMapping("/api/v1/tarefas") public class TarefaController { ... } // Abordagem 2 — como seria no Spring (exemplo, não entra no projeto) @GetMapping(value = "/api/tarefas/{id}", headers = "X-API-VERSION=1") public TarefaDTO buscarV1(@PathVariable Long id) { ... } @GetMapping(value = "/api/tarefas/{id}", headers = "X-API-VERSION=2") public TarefaV2DTO buscarV2(@PathVariable Long id) { ... }
📌 A paginação desta aula troca a resposta de GET /tarefas de uma lista ([ ... ]) para um objeto ({ "content": [...], "page": {...} }): é uma breaking change. Fazemos assim mesmo porque a API ainda está na v0.x, sem cliente em produção. Depois da v1.0.0, a mesma mudança exigiria uma /api/v2.
📄 201 com Location e Paginação na API Aula 12 do planejamento

Duas entregas da aula 12 que completam as convenções: o POST aponta para o recurso criado, e a coleção não volta inteira de uma vez.

201 Created com Location absoluto. Desde a aula 09, o Location é montado à mão (/api/v1/tarefas/9). O ServletUriComponentsBuilder parte da URL da requisição atual, então o endereço sai completo e certo mesmo se a porta ou o prefixo mudarem:

@PostMapping public ResponseEntity<TarefaDTO> criar(@Valid @RequestBody TarefaDTO dto) { TarefaDTO criada = service.criar(dto); URI location = ServletUriComponentsBuilder.fromCurrentRequest() // http://localhost:8080/api/v1/tarefas .path("/{id}") .buildAndExpand(criada.getId()) // .../tarefas/9 .toUri(); return ResponseEntity.created(location).body(criada); }

Paginação. O buscarComFiltros(TarefaFiltro, Pageable) da aula 06 já devolve Page<Tarefa>. Na API, o Spring monta o Pageable a partir de ?page=&size=&sort= e o TarefaFiltro a partir de ?prioridade=&usuarioId=:

// TarefaController.java @GetMapping public Page<TarefaDTO> listar(TarefaFiltro filtro, @PageableDefault(size = 10, sort = "id") Pageable pageable) { return service.listar(filtro, pageable); } // TarefaService.java — Page.map converte cada item e mantém os dados da página public Page<TarefaDTO> listar(TarefaFiltro filtro, Pageable pageable) { return repository.buscarComFiltros(filtro, pageable).map(this::converterParaDto); }
# application.properties — formato estável de página no JSON spring.data.web.pageable.serialization-mode=via-dto
GET {{baseUrl}}/tarefas?prioridade=ALTA&page=0&size=2&sort=prazo HTTP/1.1 200 OK Content-Type: application/json { "content": [ { "id": 1, "titulo": "Estudar JPA", "descricao": "Revisar @Entity e @Id", "prioridade": "ALTA", "prazo": "2026-11-05", "concluida": false, "usuarioId": 1 }, { "id": 6, "titulo": "Preparar apresentação", "descricao": "Slides do assunto 03", "prioridade": "ALTA", "prazo": "2026-11-08", "concluida": false, "usuarioId": 2 } ], "page": { "size": 2, "number": 0, "totalElements": 4, "totalPages": 2 } }
⚠ Sem a propriedade serialization-mode=via-dto, o Spring Boot 3.5 serializa o PageImpl como está (com pageable, sort, first, last...) e registra no console: "Serializing PageImpl instances as-is is not supported, meaning that there is no guarantee about the stability of the resulting JSON structure!". Com via-dto, a resposta vira o formato estável do PagedModel: content + page.

🚀 Curiosidades sobre REST, PATCH e ModelMapper
🎓
REST nasceu numa tese de doutorado
Roy Fielding descreveu o REST em 2000, no capítulo 5 da sua tese na Universidade da Califórnia, Irvine: Architectural Styles and the Design of Network-based Software Architectures. Ele foi um dos autores das especificações do HTTP/1.0 e do HTTP/1.1 e cofundador do projeto Apache HTTP Server. As restrições do REST eram, em boa parte, uma descrição do que fazia a Web funcionar bem.
🩹
O PATCH chegou dez anos depois
O HTTP/1.1 de 1999 (RFC 2616) não tinha PATCH. O método foi definido separadamente na RFC 5789, em 2010. A RFC deixa claro que o PATCH não é idempotente por definição: depende do formato do corpo. O nosso (copiar os campos preenchidos) é idempotente na prática, mas um PATCH do tipo "some 1 ao contador" não seria.
🔗
"REST APIs must be hypertext-driven"
Em 2008, Fielding publicou um texto com esse título reclamando que muitas APIs chamadas de REST ignoravam o hipertexto (o HATEOAS). O Modelo de Maturidade de Richardson, popularizado por Martin Fowler em 2010, coloca o HATEOAS no último nível (3). A maioria das APIs do mercado, incluindo o Task Manager, fica no nível 2: recursos e verbos HTTP.
🔁
DELETE idempotente, respostas diferentes
Idempotência fala do estado do servidor, não da resposta. No Task Manager, o primeiro DELETE /tarefas/8 responde 204 e o segundo responde 404. Mesmo assim o DELETE é idempotente: depois de uma ou de dez chamadas, a tarefa 8 continua não existindo. A RFC 9110 define assim: o efeito pretendido de várias requisições iguais é o mesmo de uma só.
❌
O "X-" dos cabeçalhos foi desaconselhado
Por muito tempo, cabeçalhos não padronizados começavam com X- (como o X-API-VERSION do slide). A RFC 6648 (2012) desaconselhou essa convenção para cabeçalhos novos, porque vários "X-" viraram padrão e o prefixo ficou para sempre no nome. Ele continua muito comum na prática, e funciona normalmente.
⚠
O aviso de sun.misc.Unsafe no console
A partir do JDK 24 (JEP 498), a JVM avisa no console quando uma biblioteca usa os métodos de acesso à memória de sun.misc.Unsafe. O ModelMapper 3.2 usa um deles internamente, então no Java 25 aparece um WARNING: A terminally deprecated method in sun.misc.Unsafe has been called quando ele é usado pela primeira vez. É só um aviso: o mapeamento funciona normalmente.
