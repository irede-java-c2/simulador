🌐 O que é um Web Service? Aula 07

É uma forma de comunicação entre aplicações através da rede (Internet).

Permite a interoperabilidade:

🔹 Um app Java pode "conversar" com um app Python.

🔹 Um app mobile (iOS/Android) pode "conversar" com um servidor Linux.

🍽 Analogia: um "garçom" (API) que pega seu pedido (requisição) e o leva para a cozinha (servidor), trazendo seu prato (resposta).

Cliente Garçom (API) Cozinha (servidor) Postman / app / site ──> GET /api/v1/tarefas/1 ──> TarefaController TarefaRepository PostgreSQL <── 200 OK + JSON <── { "id": 1, ... }

No Task Manager, quem faz o papel de garçom é o Spring Web: ele recebe a requisição HTTP, chama o método certo do controller e devolve a resposta em JSON. O cliente não precisa saber que existe um PostgreSQL nem que a API foi escrita em Java.

🔗 URIs e Recursos Aula 07

🔹 Um recurso é qualquer informação que pode ser nomeada: um usuário, um produto, um carrinho de compras, uma coleção de pedidos.

🔹 A forma como nomeamos e endereçamos esses recursos é através de uma URI (Uniform Resource Identifier).

Recurso no Task ManagerURI
A coleção de todas as tarefas/api/v1/tarefas
A tarefa de id 1/api/v1/tarefas/1
A coleção de usuários/api/v1/usuarios
O usuário de id 2/api/v1/usuarios/2
http:// localhost:8080 /api/v1 /tarefas /1 esquema servidor versão recurso id
💡 Convenção REST: URIs usam substantivos no plural (tarefas, usuarios), nunca verbos. Nada de /buscarTarefa?id=1 ou /deletarTarefa/1: quem diz a ação é o verbo HTTP (próximo card).
🚦 Os Métodos (Verbos) HTTP Aula 07 CRUD
Verbo HTTPOperação CRUDExemplo de URIDescrição
GETRead (Ler)/produtos/1Busca o produto com ID 1.
POSTCreate (Criar)/produtosCria um novo produto (dados no corpo).

DELETEDelete (Deletar)/produtos/1Remove o produto 1.

No Task Manager, a mesma tabela fica assim:

GET /api/v1/tarefas/1 // busca a tarefa 1 POST /api/v1/tarefas // cria uma tarefa (dados no corpo, em JSON) PUT /api/v1/tarefas/1 // substitui totalmente a tarefa 1 DELETE /api/v1/tarefas/1 // remove a tarefa 1

Toda resposta HTTP traz um código de status: 2xx sucesso, 4xx erro do cliente (pediu algo errado), 5xx erro do servidor. Os códigos que vamos usar estão no card "Boas Práticas em APIs RESTful".

📦 Formatos de Dados: XML vs. JSON Aula 07
XML (eXtensible Markup Language)
<usuario> <id>1</id> <nome>Ana Silva</nome> <email>ana.silva@exemplo.com</email> </usuario>
JSON (JavaScript Object Notation)
{ "id": 1, "nome": "Ana Silva", "email": "ana.silva@exemplo.com" }

O JSON é mais curto (não repete o nome de cada campo na abertura e no fechamento) e é o formato padrão do Spring Web. Quem converte objeto Java ↔ JSON é a biblioteca Jackson, que já vem no spring-boot-starter-web. Uma Tarefa do Task Manager sai assim:

{ "id": 1, "titulo": "Estudar JPA", "descricao": "Revisar @Entity e @Id", "concluida": false, "prazo": "2026-11-05", // LocalDate vira texto ISO "prioridade": "ALTA", // enum vira o nome da constante "etiquetas": [ { "id": 1, "nome": "Estudo" }, { "id": 3, "nome": "Urgente" } ] }

🗺 Mapeamento Padrão de CRUD para REST Aula 08 Spring Web

A arquitetura REST propõe um padrão claro para as operações básicas de CRUD (Create, Read, Update, Delete) sobre um recurso (ex.: Produto):

Operação CRUDVerbo HTTPURIDescrição da ação
CreatePOST/produtosCria um novo produto.
ReadGET/produtos/{id}Lê os dados de um produto específico.
UpdatePUT/produtos/{id}Substitui totalmente um produto existente.
DeleteDELETE/produtos/{id}Remove um produto específico.

Anotações do Spring Web:

AnotaçãoFunção
@RestControllerDefine a classe como um controlador REST (as respostas saem em JSON).
@RequestMapping("/api/v1/produtos")URI base para a classe.
@GetMappingMapeia requisições GET.
@PostMappingMapeia requisições POST.
@PutMappingMapeia requisições PUT.
@DeleteMappingMapeia requisições DELETE.

Recebendo dados:

🔹 @PathVariable: extrai um valor da URI. GET /produtos/{id} → public Produto get(@PathVariable Long id)

🔹 @RequestBody: converte o corpo (JSON) da requisição em um objeto Java. POST /produtos → public Produto create(@RequestBody Produto p)

// No Task Manager: a URI da classe + a do método formam o endereço final @RequestMapping("/api/v1/tarefas") // classe @GetMapping("/{id}") // método → GET /api/v1/tarefas/{id} public Tarefa buscarPorId(@PathVariable Long id) // "/tarefas/5" → id = 5 @PostMapping // POST /api/v1/tarefas public Tarefa criar(@RequestBody Tarefa tarefa) // JSON do corpo → objeto Tarefa

🗄 Conectando ao Banco de Dados com JPA Aula 08

No slide, o primeiro controller guarda os produtos em uma List na memória, que se perde a cada reinício. O próximo passo é substituir essa List volátil por um banco (no slide, o H2).

O ecossistema de persistência:

🔹 Spring Web: nossos controladores REST.

🔹 Spring Data JPA: facilita a criação de repositórios (DAOs).

🔹 Hibernate: a implementação (motor) da JPA.

🔹 H2 Database: banco de dados em memória para desenvolvimento.

Dependências (pom.xml) — slide
<dependency> <groupId>org.springframework.boot</groupId> <artifactId>spring-boot-starter-data-jpa</artifactId> </dependency> <dependency> <groupId>com.h2database</groupId> <artifactId>h2</artifactId> <scope>runtime</scope> </dependency>

Entidade: anotamos a classe de modelo Produto com @Entity e @Id.

@Entity @Table(name = "tb_produto") public class Produto { @Id @GeneratedValue(strategy = GenerationType.IDENTITY) private Long id; private String nome; // ... }

Repositório: não precisamos de código, apenas de uma interface! Ao estender JpaRepository, ganhamos de graça os métodos save() (cria e atualiza), findById() (busca por ID), findAll() (busca todos), deleteById() (deleta)... e muito mais.

⚠ Funciona, mas todas as respostas saem com 200 OK, inclusive o POST, que deveria ser 201. E um id inexistente estoura uma exceção (500). O card "Boas Práticas" corrige isso com ResponseEntity.
✅ Validações com @Valid e @NotNull Aula 08 400 Bad Request

Receber dados em um endpoint POST ou PUT é um risco. O que acontece se o cliente enviar um JSON sem o campo "nome"? Ou com um "preço" negativo? A regra de ouro da programação back-end é: "Nunca confie na entrada do usuário".

Slide
import javax.validation.constraints.*; // (ou jakarta.validation.constraints.*) @Entity @Table(name = "tb_produto") public class Produto { // ... id ... @NotBlank(message = "O nome é obrigatório") @Size(min = 3, message = "O nome deve ter no mínimo 3 caracteres") private String nome; @NotNull(message = "O preço é obrigatório") @PositiveOrZero(message = "O preço não pode ser negativo") private Double preco; // Getters e Setters... }

No Spring Boot 3 o pacote é jakarta.validation.constraints, e é preciso adicionar o starter de validação:

<dependency> <groupId>org.springframework.boot</groupId> <artifactId>spring-boot-starter-validation</artifactId> </dependency>
Tarefa.java — nome → titulo, preço → prioridade
import jakarta.validation.constraints.*; @NotBlank(message = "O título é obrigatório") @Size(min = 3, message = "O título deve ter no mínimo 3 caracteres") @Column(nullable = false, length = 100) private String titulo; @NotNull(message = "A prioridade é obrigatória") @Enumerated(EnumType.STRING) private Prioridade prioridade = Prioridade.MEDIA;

As anotações só são verificadas na chegada da requisição quando o parâmetro tem @Valid:

@PostMapping public ResponseEntity<Tarefa> criar(@Valid @RequestBody Tarefa tarefa, @RequestParam Long usuarioId)

🏅 Boas Práticas em APIs RESTful Aula 08 ResponseEntity

🔹 Use os status HTTP corretos: o status HTTP dá semântica à resposta!

StatusSignificadoNo Task Manager
200 OKSucesso (padrão, bom para GET).GET e PUT
201 CreatedRecurso criado com sucesso (ideal para POST).POST
204 No ContentSucesso sem corpo de resposta (ideal para DELETE).DELETE
400 Bad RequestErro do cliente (ex.: falha na validação).título vazio, prioridade nula
404 Not FoundRecurso não encontrado./tarefas/99, usuarioId=99

🔹 Implemente status com ResponseEntity: para ter controle total sobre o status e o corpo, trocamos o retorno do método para ResponseEntity.

@GetMapping("/{id}") public ResponseEntity<Tarefa> buscarPorId(@PathVariable Long id) { return repository.findById(id) .map(ResponseEntity::ok) // 200 + tarefa .orElse(ResponseEntity.notFound().build()); // 404 sem corpo } @PostMapping public ResponseEntity<Tarefa> criar(@Valid @RequestBody Tarefa tarefa, @RequestParam Long usuarioId) { Usuario usuario = usuarioRepository.findById(usuarioId).orElse(null); if (usuario == null) { return ResponseEntity.notFound().build(); } tarefa.setUsuario(usuario); return ResponseEntity.status(HttpStatus.CREATED).body(repository.save(tarefa)); } @DeleteMapping("/{id}") public ResponseEntity<Void> remover(@PathVariable Long id) { if (repository.findById(id).isEmpty()) { return ResponseEntity.notFound().build(); } repository.deleteById(id); return ResponseEntity.noContent().build(); // 204 }

🔹 Sempre versione sua API: o /v1 em /api/v1/tarefas permite lançar uma /api/v2 com mudanças incompatíveis sem quebrar quem já usa a v1.

🚀 Curiosidades sobre Web Services, REST e HTTP
🎓
REST nasceu em uma tese de doutorado
O termo REST foi definido por Roy Fielding em 2000, no capítulo 5 da sua tese de doutorado na Universidade da Califórnia em Irvine: "Architectural Styles and the Design of Network-based Software Architectures".
📜
O autor do REST ajudou a escrever o HTTP
Fielding também é um dos autores da especificação do HTTP/1.1 (RFC 2616, de 1999). Por isso o REST "encaixa" tão bem nos verbos e nos códigos de status do HTTP.
🧼
SOAP deixou de ser sigla
SOAP significava Simple Object Access Protocol, mas a especificação SOAP 1.2 do W3C (2003) diz que o nome não é mais um acrônimo. O protocolo em si não tem nada de "simples" nem de "objeto".
📦
JSON não foi inventado, foi "descoberto"
Douglas Crockford, que popularizou o JSON no início dos anos 2000, costuma dizer que o descobriu: ele é um subconjunto da sintaxe de objetos do JavaScript. Hoje é padronizado pela RFC 8259 e pela ECMA-404.
🫖
418 I'm a teapot
O status 418 vem da RFC 2324, uma brincadeira de 1º de abril de 1998 que especifica um protocolo para controlar cafeteiras (HTCPCP). Um bule de chá que recebe um pedido de café responde "Eu sou um bule".
📮
O Postman começou como projeto paralelo
O Postman foi criado em 2012 por Abhinav Asthana como um projeto paralelo, distribuído como aplicativo do Chrome, para facilitar o teste de APIs. Depois virou aplicativo próprio para desktop e web.
