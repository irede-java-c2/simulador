🔗 Mapeamento de Relações Aula 03

No mundo real, os objetos raramente existem de forma isolada. Um Cliente faz vários Pedidos; um Pedido pertence a um único Cliente. Essa é a essência do relacionamento um-para-muitos (1:N), a associação mais comum em sistemas de software.

No Task Manager, a mesma ideia aparece entre Usuario e Tarefa:

Exemplo do slideTask ManagerCardinalidade
Um Cliente faz vários PedidosUm Usuario tem várias Tarefas1:N
Um Pedido pertence a um único ClienteUma Tarefa pertence a um único UsuarioN:1

🔹 1:N e N:1 são a mesma relação, vista de lados diferentes. Olhando do usuário, ele tem muitas tarefas; olhando da tarefa, ela tem um usuário.

🔹 No Task Manager não existe entidade Projeto: as tarefas pertencem diretamente ao usuário.

🔀 O Conceito 1:N Aula 03 Objeto × Tabela

🔹 No paradigma de objetos: a relação é representada por um atributo.

🔹 No paradigma relacional: a relação é mantida através de uma chave estrangeira (Foreign Key).

🔹 O trabalho do ORM é conectar esses dois mundos usando anotações.

// Mundo dos objetos: referências Tarefa ──── usuario ────> Usuario Usuario ──── tarefas ────> List<Tarefa> -- Mundo relacional: uma coluna FK no lado "muitos" usuarios tarefas ┌────┬──────┐ ┌────┬─────────────┬─────────────────┐ │ id │ nome │ │ id │ titulo │ usuario_id (FK) │ ├────┼──────┤ ├────┼─────────────┼─────────────────┤ │ 1 │ Ana │ <───── │ 1 │ Estudar JPA │ 1 │ │ │ │ <───── │ 2 │ Revisar PR │ 1 │ └────┴──────┘ └────┴─────────────┴─────────────────┘

Repare na assimetria: no Java a relação pode existir dos dois lados (o usuário conhece sua lista e a tarefa conhece seu usuário), mas no banco existe uma única coluna, tarefas.usuario_id. A FK sempre fica na tabela do lado "muitos".

📐 O slide traz o diagrama entidade-relacionamento "FUNCIONÁRIO — TRABALHA EM — DEPARTAMENTO" (1:N), do artigo citado nos Links. No Task Manager, o mesmo desenho seria: USUARIO — POSSUI — TAREFA.
🏷 Anotações-Chave: @ManyToOne e @OneToMany Aula 03
AnotaçãoOnde usarO que faz
@ManyToOne
(Muitos-para-Um)		Na classe que representa o lado "muitos" da relação.Anotada sobre o atributo que representa a referência única ao "pai" (ex.: private Cliente cliente;).
@OneToMany
(Um-para-Muitos)		Na classe que representa o lado "um" da relação.Anotada sobre a coleção de entidades filhas (ex.: private List<Pedido> pedidos;).
Tarefa.java — lado "muitos" (lado dono)
@Entity @Table(name = "tarefas") public class Tarefa { // id, titulo, descricao, prioridade, prazo, concluida... @ManyToOne @JoinColumn(name = "usuario_id", nullable = false) private Usuario usuario; // referência única ao "pai" }
Usuario.java — lado "um" (lado inverso)
@Entity @Table(name = "usuarios") public class Usuario { @Id @GeneratedValue(strategy = GenerationType.IDENTITY) private Long id; @Column(nullable = false) private String nome; @Column(nullable = false, unique = true) private String email; @OneToMany(mappedBy = "usuario") private List<Tarefa> tarefas = new ArrayList<>(); // coleção de filhas }

🔹 Lado dono: é o lado que tem a FK, aqui Tarefa.usuario. Só ele decide o valor de usuario_id no banco. A anotação @JoinColumn dá nome à coluna (sem ela, o padrão também seria usuario_id: nome do atributo + _ + nome da PK).

🔹 Lado inverso: usa mappedBy = "usuario", o nome do atributo do outro lado (não o nome da coluna). Ele diz ao Hibernate: "esta lista é um espelho; a FK já está mapeada em Tarefa.usuario".

SQL gerado no console (show-sql)
Hibernate: create table usuarios (id bigint generated by default as identity, email varchar(255) not null, nome varchar(255) not null, primary key (id)) Hibernate: create table tarefas (concluida boolean not null, prazo date, id bigint generated by default as identity, usuario_id bigint not null, descricao varchar(255), prioridade varchar(255) check (prioridade in ('BAIXA','MEDIA','ALTA')), titulo varchar(255) not null, primary key (id)) Hibernate: alter table if exists usuarios drop constraint if exists UKkfsp0s1tflm1cwlj8idhqsad0 Hibernate: alter table if exists usuarios add constraint UKkfsp0s1tflm1cwlj8idhqsad0 unique (email) Hibernate: alter table if exists tarefas add constraint FKp2d8qq1y6x3rjv0n5kwe7tb4l foreign key (usuario_id) references usuarios
⚠ Se você esquecer o mappedBy, o Hibernate entende que existem DUAS relações independentes e cria uma tabela extra (usuarios_tarefas) para o @OneToMany. Sinal clássico de mapeamento errado: uma tabela que você não pediu aparecendo no console.

🕸 Mapeamento ManyToMany Aula 04 N:N

O conceito N:N:

🔹 Um relacionamento N:N não pode ser representado diretamente;

🔹 É necessária uma terceira tabela, conhecida como tabela de junção (ou tabela associativa/intermediária);

🔹 Essa tabela contém, no mínimo, duas colunas de chave estrangeira.

O slide usa Autor × Livro (um autor escreve vários livros e um livro pode ter vários autores), com a tabela AutorLivro(ID_AUTOR, ID_LIVRO). No Task Manager, a relação N:N é Tarefa × Etiqueta: uma tarefa pode ter várias etiquetas ("estudo", "urgente") e uma etiqueta classifica várias tarefas.

tarefas tarefa_etiqueta etiquetas ┌────┬─────────────┐ ┌───────────┬─────────────┐ ┌────┬─────────┐ │ id │ titulo │ │ tarefa_id │ etiqueta_id │ │ id │ nome │ ├────┼─────────────┤ ├───────────┼─────────────┤ ├────┼─────────┤ │ 1 │ Estudar JPA │ │ 1 │ 1 │ │ 1 │ estudo │ │ 2 │ Revisar PR │ │ 1 │ 2 │ │ 2 │ urgente │ └────┴─────────────┘ │ 2 │ 2 │ └────┴─────────┘ └───────────┴─────────────┘ -- "Estudar JPA" tem as etiquetas estudo e urgente; "Revisar PR" tem só urgente.

Por que não dá para ter uma FK direto em tarefas? Porque uma coluna guarda um único valor. Uma coluna etiqueta_id em tarefas permitiria só uma etiqueta por tarefa. Cada linha da tabela de junção representa um par (tarefa, etiqueta).

🏷 Anotação-Chave: @ManyToMany Aula 04

🔹 Onde usar: em ambas as entidades da relação, sobre os atributos de coleção.

🔹 Lado dono: assim como na relação 1:N, precisamos definir um lado dono, que será responsável pela configuração da tabela de junção. O outro lado será o inverso e usará o mappedBy.

🔹 Customização com @JoinTable: usamos essa anotação no lado dono para configurar a tabela de junção.

Tarefa.java — lado dono
@ManyToMany @JoinTable( name = "tarefa_etiqueta", // nome da tabela de junção joinColumns = @JoinColumn(name = "tarefa_id"), // FK para ESTE lado inverseJoinColumns = @JoinColumn(name = "etiqueta_id") // FK para o OUTRO lado ) private Set<Etiqueta> etiquetas = new HashSet<>();
Etiqueta.java — lado inverso
@Entity @Table(name = "etiquetas") public class Etiqueta { @Id @GeneratedValue(strategy = GenerationType.IDENTITY) private Long id; @Column(nullable = false, unique = true, length = 50) private String nome; @ManyToMany(mappedBy = "etiquetas") private Set<Tarefa> tarefas = new HashSet<>(); }
SQL gerado no console
Hibernate: create table etiquetas (id bigint generated by default as identity, nome varchar(50) not null, primary key (id)) Hibernate: create table tarefa_etiqueta (etiqueta_id bigint not null, tarefa_id bigint not null, primary key (etiqueta_id, tarefa_id)) Hibernate: alter table if exists tarefa_etiqueta add constraint FK9c1xg3nqw0hb7jvo2ms5k8ldr foreign key (etiqueta_id) references etiquetas Hibernate: alter table if exists tarefa_etiqueta add constraint FKr4ty6s0m8ue2qa9xj1kh3wp7n foreign key (tarefa_id) references tarefas

🔹 Em N:N, a escolha do lado dono é sua. No Task Manager escolhemos Tarefa, porque é natural "colocar etiquetas em uma tarefa". Só alterações na coleção do lado dono (tarefa.getEtiquetas()) geram INSERT/DELETE na tarefa_etiqueta.

💡 Usamos Set em vez de List: com Set, a chave primária da tarefa_etiqueta é o par (etiqueta_id, tarefa_id), o que impede duplicatas, e remover uma etiqueta gera um único DELETE. Como Etiqueta vai para um HashSet, ela precisa de equals() e hashCode() bem feitos (veja Boas Práticas).
🌊 Cascateamento Aula 04 cascade

🔹 O problema: salvar um Cliente não salva automaticamente seus Pedidos associados. No Task Manager: salvar um Usuario novo não salva as tarefas novas da sua lista.

🔹 A solução: cascade = CascadeType.PERSIST (ou ALL).

// Exemplo do slide — na classe Cliente @OneToMany(mappedBy = "cliente", cascade = CascadeType.ALL) private List<Pedido> pedidos; // Task Manager — na classe Usuario @OneToMany(mappedBy = "usuario", cascade = CascadeType.ALL, orphanRemoval = true) private List<Tarefa> tarefas = new ArrayList<>();

🔹 Com isso: entityManager.persist(cliente); agora salva o cliente e todos os pedidos da lista. No Spring, usuarioRepository.save(usuario) chama o persist e salva o usuário e as tarefas.

CascadeTypePropaga a operação...
PERSISTsalvar um objeto novo (persist)
MERGEatualizar um objeto destacado (merge)
REMOVEapagar (remove)
REFRESH / DETACHrecarregar do banco / desanexar do contexto
ALLtodas as anteriores
⚠ Cuidado com CascadeType.REMOVE! Ele pode apagar dados em cadeia. Em Usuario.tarefas faz sentido (as tarefas pertencem ao usuário). Em Tarefa.etiquetas (N:N) seria um desastre: apagar uma tarefa apagaria a etiqueta "urgente" — que outras tarefas usam. Por isso, no N:N usamos só cascade = {CascadeType.PERSIST, CascadeType.MERGE}.

🔹 orphanRemoval = true (complemento): uma tarefa retirada da lista com usuario.removerTarefa(t) vira "órfã" e é apagada do banco. Diferença: REMOVE age quando o pai é apagado; orphanRemoval age quando o filho sai da coleção.

🚚 Tipos de Carregamento (Fetch) Aula 04 LAZY × EAGER
FetchType.LAZY — padrão para coleçõesFetchType.EAGER — padrão para referências únicas
🔹 Traz o Cliente, mas não os Pedidos.
🔹 Os Pedidos só são buscados do banco quando você os acessa (cliente.getPedidos()).
🔹 Vantagem: performance!		 🔹 Traz o Cliente e os Pedidos juntos (com uma consulta extra ou JOIN).
🔹 Desvantagem: pode ser lento e carregar dados desnecessários.

Os padrões da JPA, anotação por anotação:

@ManyToManyLAZYTarefa.etiquetas — mantém LAZY

// Tarefa.java — revisão da aula 04 @ManyToOne(fetch = FetchType.LAZY) @JoinColumn(name = "usuario_id", nullable = false) private Usuario usuario;
Com LAZY: o usuário só é buscado quando acessado
Usuario ana = usuarioRepository.findById(1L).orElseThrow(); Hibernate: select u1_0.id,u1_0.email,u1_0.nome from usuarios u1_0 where u1_0.id=? ana.getTarefas().size(); // só agora a coleção é carregada Hibernate: select t1_0.usuario_id,t1_0.id,t1_0.concluida,t1_0.descricao,t1_0.prazo,t1_0.prioridade,t1_0.titulo from tarefas t1_0 where t1_0.usuario_id=?
📌 Com EAGER em uma referência única (Tarefa.usuario, o padrão do @ManyToOne), buscar uma tarefa traz o usuário junto, por JOIN ou por um SELECT extra. Parece cômodo, mas ao listar 100 tarefas o Hibernate pode disparar um SELECT por usuário diferente: o problema N+1 (simulador "Laboratório de fetch").
✅ Boas Práticas Aula 04 4 regras

🔹 1. Sincronize os dois lados: use métodos add/remove para manter a consistência do grafo de objetos em memória.

// Usuario.java public void adicionarTarefa(Tarefa tarefa) { tarefas.add(tarefa); tarefa.setUsuario(this); // lado dono: é isto que grava a FK } public void removerTarefa(Tarefa tarefa) { tarefas.remove(tarefa); tarefa.setUsuario(null); } // Tarefa.java public void adicionarEtiqueta(Etiqueta etiqueta) { etiquetas.add(etiqueta); etiqueta.getTarefas().add(this); } public void removerEtiqueta(Etiqueta etiqueta) { etiquetas.remove(etiqueta); etiqueta.getTarefas().remove(this); }

🔹 2. Evite a LazyInitializationException: inicialize as coleções antes de fechar a sessão ou use JOIN FETCH. No Spring, a sessão fica aberta enquanto durar a transação, então quem acessa relações LAZY precisa estar em um método @Transactional.

org.hibernate.LazyInitializationException: failed to lazily initialize a collection of role: br.org.irede.taskmanagerapi.model.Usuario.tarefas: could not initialize proxy - no Session

🔹 3. Use EAGER com extrema cautela para evitar o problema N+1: 1 consulta traz a lista e, para cada item, sai mais uma consulta para buscar a relação. O JOIN FETCH, que resolve o N+1 buscando tudo em uma consulta, é tema da aula 05 (JPQL).

🔹 4. equals() e hashCode(): implemente-os usando chaves de negócio, nunca o ID gerado.

// Etiqueta.java — "nome" é único: é a chave de negócio @Override public boolean equals(Object o) { if (this == o) return true; if (!(o instanceof Etiqueta outra)) return false; return Objects.equals(nome, outra.nome); } @Override public int hashCode() { return Objects.hash(nome); }
🤔 Por que nunca o ID gerado? Com IDENTITY, o id é null até o INSERT. Uma Etiqueta nova entra no HashSet com um hashCode e, depois do save, o id muda e o hashCode muda junto. O objeto fica "perdido" dentro do próprio Set: contains() e remove() deixam de encontrá-lo. A chave de negócio (Etiqueta.nome, Usuario.email) existe desde o new.

🚀 Curiosidades sobre Relacionamentos e JPA
📐
O diagrama do slide tem quase 50 anos
Os losangos e retângulos do diagrama "Funcionário — trabalha em — Departamento" vêm do Modelo Entidade-Relacionamento, proposto por Peter Chen em 1976 no artigo "The Entity-Relationship Model — Toward a Unified View of Data".
💭
LAZY é só um "pedido"
Pela especificação JPA, EAGER é uma obrigação do provedor, mas LAZY é apenas uma dica (hint): o provedor pode carregar antes do necessário. O Hibernate respeita o LAZY usando proxies e coleções especiais, como a PersistentBag.
🐢
O próprio Hibernate recomenda LAZY
O guia oficial do Hibernate recomenda marcar todas as associações como LAZY e decidir o carregamento antecipado na consulta, com JOIN FETCH ou entity graphs. Por isso trocamos o @ManyToOne de Tarefa.usuario para LAZY na aula 04.
👻
A tabela fantasma do @OneToMany
Um @OneToMany sem mappedBy e sem @JoinColumn é, pela especificação, uma relação unidirecional com tabela de junção. Por isso, ao esquecer o mappedBy, aparece uma tabela usuarios_tarefas que ninguém pediu.
👜
List ou Set no @ManyToMany?
Para o Hibernate, uma List sem @OrderColumn é um bag. Ao remover uma etiqueta de um bag N:N, ele apaga todas as linhas da tarefa na tarefa_etiqueta e reinsere as que sobraram. Com Set, sai um único DELETE.
🐘
"generated by default as identity"
As colunas identity do padrão SQL chegaram ao PostgreSQL 10 (2017). Antes, o caminho era o tipo serial. Hoje o Hibernate usa bigint generated by default as identity quando a entidade tem GenerationType.IDENTITY.
