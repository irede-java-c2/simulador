❓ O que é JPQL? Aula 05

A JPQL (Jakarta Persistence Query Language) é uma linguagem de consulta orientada a objetos, muito semelhante à sintaxe do SQL, mas com uma diferença fundamental: ela opera sobre as suas entidades e seus atributos, não sobre tabelas e colunas.

Isso a torna independente do banco de dados: você escreve a consulta uma vez e o Hibernate a traduz para o SQL do banco configurado (o dialeto, que no Task Manager é o do PostgreSQL).

Fonteentidade Tarefatabela tarefas
Camposatributos t.prazo, t.usuariocolunas prazo, usuario_id
Retornoobjetos Tarefalinhas e colunas
Bancoqualquer um com dialetoespecífico (PostgreSQL)
-- JPQL SELECT t FROM Tarefa t WHERE t.concluida = false
Console (show-sql + format_sql ligados no application.properties)
Hibernate: select t1_0.id, t1_0.concluida, t1_0.descricao, t1_0.prazo, t1_0.prioridade, t1_0.titulo, t1_0.usuario_id from tarefas t1_0 where t1_0.concluida=false

🔹 Tarefa é o nome da classe (com T maiúsculo). Escrever FROM tarefas na JPQL gera erro: Could not resolve root entity 'tarefas'.

🔹 t é o alias (apelido) da entidade, usado para acessar os atributos (t.titulo, t.usuario.email).

🔹 De onde vem o em? No loja você o criava com o JPAUtil. No Spring Boot, basta pedir que ele seja injetado:

@PersistenceContext private EntityManager em; // jakarta.persistence.EntityManager

🔹 O jeito Spring Data: @Query. No TarefaRepository, a mesma JPQL vira um método. O Spring cria a TypedQuery, preenche os parâmetros e chama getResultList() por você:

public interface TarefaRepository extends JpaRepository<Tarefa, Long> { @Query("SELECT t FROM Tarefa t WHERE t.concluida = false") List<Tarefa> listarPendentes(); @Query("SELECT t FROM Tarefa t WHERE t.prioridade = :prioridade AND t.concluida = :concluida") List<Tarefa> buscarPorPrioridade(@Param("prioridade") Prioridade prioridade, @Param("concluida") boolean concluida); }
💡 Use sempre parâmetros (:prioridade) em vez de concatenar valores na string. O valor viaja separado da consulta, e o Hibernate cuida do tipo (o enum vira o texto 'ALTA' por causa do EnumType.STRING). Imports: org.springframework.data.jpa.repository.Query e org.springframework.data.repository.query.Param.
🔗 JOIN, JOIN FETCH e Agregações Aula 05 Relações

As relações mapeadas no assunto 02 agora viram caminhos nas consultas. Três usos que entram no TarefaRepository:

🔹 JOIN para filtrar por um atributo da entidade relacionada (inclusive em N:N):

@Query("SELECT t FROM Tarefa t JOIN t.etiquetas e WHERE e.nome = :nome") List<Tarefa> listarPorEtiqueta(@Param("nome") String nome);
from tarefas t1_0 join tarefa_etiqueta e1_0 on t1_0.id=e1_0.tarefa_id join etiquetas e1_1 on e1_1.id=e1_0.etiqueta_id where e1_1.nome=?

🔹 JOIN FETCH para carregar junto: o JOIN comum só filtra; o JOIN FETCH também traz o usuário no mesmo SELECT. É a cura do problema N+1 visto na aula 04:

@Query("SELECT t FROM Tarefa t JOIN FETCH t.usuario u WHERE u.email = :email ORDER BY t.prazo") List<Tarefa> listarPorUsuario(@Param("email") String email);

🔹 Funções de agregação (COUNT, SUM, AVG, MIN, MAX) com GROUP BY. Quando o SELECT devolve mais de um valor, cada linha vem como um Object[]:

@Query("SELECT t.prioridade, COUNT(t) FROM Tarefa t GROUP BY t.prioridade") List<Object[]> contarPorPrioridade(); // uso for (Object[] linha : tarefaRepository.contarPorPrioridade()) { System.out.println(linha[0] + ": " + linha[1]); // ALTA: 3 }
📌 Como Tarefa.usuario usa o fetch padrão do @ManyToOne (EAGER), uma JPQL sem JOIN FETCH faz o Hibernate disparar SELECTs extras em usuarios logo depois da consulta. Com JOIN FETCH, tudo vem em uma ida ao banco.
🏗 Criteria API Aula 06

🔹 API fluente e programática para construir consultas. Em vez de escrever uma String, você usa objetos e métodos para montar a consulta passo a passo.

🔹 Vantagens:

VantagemO que significa
Segurança de Tipo (Type-Safety)A consulta é código Java: CriteriaQuery<Tarefa> só devolve Tarefa, e o compilador confere os tipos de métodos e parâmetros. Um erro de digitação dentro de uma String JPQL só aparece quando a consulta é criada.
Criação DinâmicaPartes da consulta podem ser incluídas ou não com if, sem concatenar pedaços de String. Ideal para telas de busca com filtros opcionais.
// JPQL: a consulta é uma String "SELECT t FROM Tarefa t WHERE t.prioridade = :prioridade" // Criteria: a mesma consulta, montada com objetos cq.select(root).where(cb.equal(root.get("prioridade"), prioridade));

🛠 Consulta Criteria API Aula 06 4 etapas

O código do slide (produtos com preço maior que 500) traduzido para tarefas com prazo depois de 12/11/2026:

// 1. Obter os objetos de base CriteriaBuilder cb = em.getCriteriaBuilder(); CriteriaQuery<Tarefa> cq = cb.createQuery(Tarefa.class); Root<Tarefa> root = cq.from(Tarefa.class); // FROM Tarefa // 2. Construir a cláusula SELECT (neste caso, a entidade inteira) cq.select(root); // SELECT t // 3. Construir a cláusula WHERE (os predicados) ParameterExpression<LocalDate> prazoParam = cb.parameter(LocalDate.class); Predicate predicado = cb.greaterThan(root.get("prazo"), prazoParam); // WHERE t.prazo > ? cq.where(predicado); // 4. Criar e executar a TypedQuery TypedQuery<Tarefa> query = em.createQuery(cq); query.setParameter(prazoParam, LocalDate.of(2026, 11, 12)); List<Tarefa> tarefas = query.getResultList();

↕ Ordenação de Resultados Aulas 05 e 06 ORDER BY

Ordenação com JPQL: a cláusula ORDER BY funciona de forma muito similar ao SQL. Você especifica o atributo da entidade pelo qual deseja ordenar, seguido opcionalmente por ASC (ascendente, o padrão) ou DESC (descendente).

// Ordenar tarefas pelo título em ordem alfabética SELECT t FROM Tarefa t ORDER BY t.titulo ASC // Ordenar tarefas do prazo mais distante para o mais próximo SELECT t FROM Tarefa t ORDER BY t.prazo DESC // Vários critérios: primeiro o prazo; no empate, o título SELECT t FROM Tarefa t ORDER BY t.prazo ASC, t.titulo ASC

🔹 Na Criteria API, a ordenação é criada pelo CriteriaBuilder:

cq.orderBy(cb.asc(root.get("prazo")), cb.asc(root.get("titulo"))); cq.orderBy(cb.desc(root.get("prazo")));
⚠ Duas pegadinhas no PostgreSQL: (1) com EnumType.STRING, ORDER BY t.prioridade ordena o texto: ALTA, BAIXA, MEDIA (ordem alfabética, não de importância). (2) Em DESC, os valores NULL aparecem primeiro: tarefas sem prazo vão para o topo da lista.
📄 Paginação de Resultados Aula 06 OFFSET / FETCH

Paginação é o ato de dividir um grande conjunto de resultados em "páginas" menores e mais gerenciáveis. O código do slide, com tarefas:

public List<Tarefa> buscarTarefasPaginado(int pagina, int tamanhoPagina) { String jpql = "SELECT t FROM Tarefa t ORDER BY t.prazo DESC"; int primeiroResultado = (pagina - 1) * tamanhoPagina; return em.createQuery(jpql, Tarefa.class) .setFirstResult(primeiroResultado) .setMaxResults(tamanhoPagina) .getResultList(); } // Chamada do método para buscar a página 2, com 3 tarefas por página: // List<Tarefa> tarefasDaPagina2 = buscarTarefasPaginado(2, 3);

🔹 A paginação acontece no banco: setFirstResult vira OFFSET e setMaxResults vira FETCH FIRST. Só as linhas da página trafegam até o Java.

🔹 Sempre ordene ao paginar. Sem ORDER BY, o banco não garante a ordem, e uma tarefa pode aparecer em duas páginas (ou em nenhuma).

🔹 No Spring Data, a paginação usa Pageable e devolve um Page, que já traz o total de registros e de páginas:

@Query("SELECT t FROM Tarefa t WHERE t.concluida = false") Page<Tarefa> listarPendentes(Pageable pageable); // uso: página 2 (índice 1!), 3 por página, ordenadas por prazo Page<Tarefa> pagina = tarefaRepository.listarPendentes( PageRequest.of(1, 3, Sort.by("prazo"))); pagina.getContent(); // as tarefas da página pagina.getTotalElements(); // 5 (faz um SELECT count(...) a mais) pagina.getTotalPages(); // 2
⚠ No slide, a página começa em 1 (por isso o pagina - 1). No Spring Data, o PageRequest.of(pagina, tamanho) começa em 0: PageRequest.of(1, 3) é a segunda página.
🎛 Filtros Dinâmicos com Criteria API Aula 06 List<Predicate>

A verdadeira força da Criteria API está na construção de consultas com filtros dinâmicos. Imagine uma tela de busca de tarefas onde o usuário pode preencher parte do título, um prazo mínimo e uma prioridade, todos opcionais. (No slide: nome, preço mínimo e categoria do produto.)

public List<Tarefa> buscaDinamica(String titulo, LocalDate prazoMin, Prioridade prioridade) { CriteriaBuilder cb = em.getCriteriaBuilder(); CriteriaQuery<Tarefa> cq = cb.createQuery(Tarefa.class); Root<Tarefa> root = cq.from(Tarefa.class); List<Predicate> predicates = new ArrayList<>(); if (titulo != null && !titulo.trim().isEmpty()) { predicates.add(cb.like(root.get("titulo"), "%" + titulo + "%")); } if (prazoMin != null) { predicates.add(cb.greaterThanOrEqualTo(root.get("prazo"), prazoMin)); } if (prioridade != null) { predicates.add(cb.equal(root.get("prioridade"), prioridade)); } // Combina todos os predicados da lista com "AND" cq.where(predicates.toArray(new Predicate[0])); return em.createQuery(cq).getResultList(); }
ChamadaWHERE geradoResultado (ids)
buscaDinamica(null, null, null)sem WHERE1 a 7
buscaDinamica("JPQL", null, null)titulo like ?3
buscaDinamica(null, 12/11, ALTA)prazo>=? and prioridade=?5
buscaDinamica("a", 10/11, null)titulo like ? and prazo>=?3, 4, 5, 6, 7

🔹 Cada filtro preenchido vira um Predicate na lista. O cq.where(...) com vários predicados os combina com AND; com a lista vazia, a consulta fica sem WHERE e devolve tudo.

🔹 Em JPQL, o mesmo resultado exigiria montar a String com vários if e cuidar de onde entra o WHERE e onde entra o AND. É aí que a Criteria brilha.

💡 No PostgreSQL, LIKE diferencia maiúsculas de minúsculas: "jpql" não encontra "Escrever consultas JPQL". Para ignorar a caixa, use cb.like(cb.lower(root.get("titulo")), "%" + titulo.toLowerCase() + "%").

🔹 SQL nativo no Spring Data: @Query com nativeQuery = true. Você escreve o SQL do PostgreSQL, com nomes de tabelas e colunas, e o Hibernate envia o texto como está. Útil para recursos que só o banco tem, como o ILIKE (LIKE sem diferenciar maiúsculas) do PostgreSQL:

🚀 Curiosidades sobre JPQL, Criteria e Paginação
🧬
A JPQL tem um "avô": o EJB QL
A JPQL nasceu no JPA 1.0 (2006, JSR 220) como evolução do EJB QL, a linguagem de consulta dos entity beans do EJB 2.0. Com o JPA, a mesma ideia de "consultar objetos, não tabelas" passou a valer para classes Java comuns anotadas com @Entity.
🏗
Criteria API: padrão desde o JPA 2.0
A Criteria API entrou na especificação no JPA 2.0 (2009, JSR 317). Antes disso, o Hibernate já tinha a sua própria API de critérios (org.hibernate.Criteria), que foi depreciada no Hibernate 5.2 e removida no Hibernate 6. Hoje o caminho é a Criteria do Jakarta Persistence, a mesma do slide.
🧠
JPQL e Criteria viram a mesma coisa por dentro
No Hibernate 6, tanto a String JPQL/HQL quanto a Criteria são convertidas para uma mesma árvore interna, o SQM (Semantic Query Model), e só então traduzidas para o SQL do dialeto. Por isso as duas geram exatamente o mesmo SQL no simulador.
📏
OFFSET ... FETCH FIRST é SQL padrão
O LIMIT que muita gente usa no PostgreSQL e no MySQL não faz parte do padrão SQL. A forma OFFSET n ROWS FETCH FIRST m ROWS ONLY foi padronizada no SQL:2008, e é ela que o Hibernate 6 gera para o PostgreSQL ao traduzir setFirstResult e setMaxResults.
🐢
Páginas muito distantes custam caro
A documentação do PostgreSQL avisa: as linhas puladas pelo OFFSET ainda precisam ser calculadas pelo servidor. Pedir a página 10.000 obriga o banco a percorrer e descartar todas as linhas anteriores. Para listas enormes, existe a paginação por chave (keyset): "me dê as próximas 10 depois do prazo X".
🐘
ILIKE é coisa do PostgreSQL
O ILIKE, que compara texto sem diferenciar maiúsculas e minúsculas, não está no padrão SQL: é uma extensão do PostgreSQL. Esse é o tipo de recurso que justifica o SQL nativo e que explica a "portabilidade baixa" da tabela do slide: a mesma consulta falharia em outro banco.
