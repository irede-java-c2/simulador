📡 Tratamento de Erros e Códigos HTTP Aula 09

Em um sistema de Web Services, a comunicação é a chave. Quando um cliente (um app mobile, um frontend web) faz uma requisição à sua API, ele não pode ver seu console ou seus logs. A única resposta que ele recebe é a Resposta HTTP.

// O que o SERVIDOR vê (console do NetBeans): ERROR ... [dispatcherServlet] : Servlet.service() ... threw exception [Request processing failed: java.lang.RuntimeException: Não encontrado!] // O que o CLIENTE vê (Postman): HTTP/1.1 500 Internal Server Error { "status": 500, "error": "Internal Server Error", "path": "/api/v1/tarefas/99" }

🔹 Para o cliente, "a tarefa 99 não existe" e "o servidor quebrou" ficaram iguais. Tratar erros é escolher o status certo e um corpo que explique o que aconteceu.

🚦 Código de Status HTTP e Códigos Essenciais Aula 09 2xx · 4xx · 5xx
ClasseSignificado (slide)
2xx SucessoA requisição foi recebida, compreendida e aceita com sucesso.
4xx Erro do ClienteA requisição está incorreta e o servidor não pode processá-la.
5xx Erro do ServidorA requisição é válida, mas o servidor falhou ao tentar processá-la.

🔹 Códigos essenciais para um desenvolvedor, e onde cada um aparece no Task Manager:

CódigoSignificado (slide)No Task Manager
200 OKA resposta padrão para sucesso.GET e PUT de tarefas
201 CreatedSucesso de um POST que resultou na criação de um novo recurso.POST /tarefas
204 No ContentRequisição processada, mas não há nada para retornar no corpo.DELETE /tarefas/{id}
400 Bad RequestEm APIs REST, mais comum em falhas de validação (campo obrigatório não enviado, e-mail em formato inválido).título vazio ou prioridade nula
401 UnauthorizedO cliente não forneceu as credenciais de autenticação necessárias.sem token JWT (aula 14)
403 ForbiddenO cliente está autenticado, mas não tem permissão para acessar o recurso.tarefa de outro usuário (aula 14)
404 Not FoundO servidor não encontrou o recurso solicitado na URI especificada./tarefas/99
500 Internal Server ErrorAlgo inesperado aconteceu no back-end.exceção não tratada
💡 Regra prática: se o problema está na requisição (dado inválido, id inexistente), a resposta é 4xx e o cliente pode corrigir. Se o problema está no servidor, é 5xx. Um 500 para "tarefa não encontrada" é um bug da API.
📦 Uso de ResponseEntity para Retorno Personalizado Aula 09

ResponseEntity é uma classe do Spring que encapsula toda a resposta HTTP. Ela é composta por três partes principais:

ParteDescrição (slide)Na resposta HTTP
Corpo (Body) TO objeto que será serializado em JSON (ex.: uma Tarefa ou uma mensagem de erro).{ "id": 9, ... }
StatusO código de status (ex.: HttpStatus.OK, HttpStatus.NOT_FOUND).HTTP/1.1 201 Created
Cabeçalhos (Headers)(Opcional) Metadados HTTP (ex.: o cabeçalho Location em um 201).Location: /api/v1/tarefas/9
ResponseEntity.ok(tarefa) // 200 + corpo ResponseEntity.created(location).body(tarefa) // 201 + Location + corpo ResponseEntity.noContent().build() // 204, sem corpo ResponseEntity.notFound().build() // 404, sem corpo ResponseEntity.badRequest().body(erro) // 400 + corpo ResponseEntity.status(HttpStatus.NOT_FOUND).body(erro) // qualquer status + corpo

🔹 O tipo entre <> é o tipo do corpo: ResponseEntity<Tarefa>, ResponseEntity<String>, ou ResponseEntity<Void> quando não há corpo. Import: org.springframework.http.ResponseEntity (e HttpStatus, do mesmo pacote).

🔄 GET 200/404, POST 201 e DELETE 204: Antes e Depois Aula 09 3 refatorações

🔹 GET (Buscar por ID): retornando 200 ou 404. Antes, uma RuntimeException sem tratamento estoura 500:

// Antes @GetMapping("/{id}") public Tarefa buscarPorId(@PathVariable Long id) { return repository.findById(id) .orElseThrow(() -> new RuntimeException("Não encontrado!")); // Estoura 500! } // Depois import org.springframework.http.ResponseEntity; @GetMapping("/{id}") public ResponseEntity<Tarefa> buscarPorId(@PathVariable Long id) { Optional<Tarefa> tarefa = repository.findById(id); if (tarefa.isPresent()) { return ResponseEntity.ok(tarefa.get()); // Retorna 200 OK com a tarefa no corpo } else { return ResponseEntity.notFound().build(); // Retorna 404 Not Found sem corpo } }

🔹 POST (Criar): retornando 201 Created. Por padrão, um POST que devolve o objeto responde 200. A boa prática é 201 com a URI do novo recurso no cabeçalho Location:

// Antes @PostMapping public Tarefa criar(@RequestBody Tarefa tarefa, @RequestParam Long usuarioId) { ... return repository.save(tarefa); // Retorna 200 OK } // Depois import java.net.URI; @PostMapping public ResponseEntity<Tarefa> criar(@Valid @RequestBody Tarefa tarefa, @RequestParam Long usuarioId) { ... Tarefa tarefaSalva = repository.save(tarefa); // Boa prática: Retornar a URI do novo recurso no cabeçalho "Location" URI location = URI.create("/api/v1/tarefas/" + tarefaSalva.getId()); return ResponseEntity.created(location).body(tarefaSalva); // Retorna 201 Created }

🔹 DELETE (Deletar): retornando 204 No Content. Forçar 200 com @ResponseStatus "não é o ideal": não há nada para devolver.

// Antes @DeleteMapping("/{id}") @ResponseStatus(HttpStatus.OK) // Não é o ideal public void remover(@PathVariable Long id) { repository.deleteById(id); // Retorna 200 OK com corpo vazio } // Depois @DeleteMapping("/{id}") public ResponseEntity<Void> remover(@PathVariable Long id) { if (!repository.existsById(id)) { return ResponseEntity.notFound().build(); // Retorna 404 se não existir } repository.deleteById(id); return ResponseEntity.noContent().build(); // Retorna 204 No Content }
📌 Boa parte disso você já fez na aula 08. A novidade aqui é o Location no 201. Repare também no existsById: no Spring Data 3, deleteById de um id inexistente não lança erro. Sem a verificação, o DELETE da tarefa 99 responderia sucesso sem ter apagado nada.
🚨 Exceções Customizadas Aula 09 RuntimeException

Crie exceções claras que representem seus erros de negócio. No pacote exception:

package br.org.irede.taskmanagerapi.exception; public class ResourceNotFoundException extends RuntimeException { public ResourceNotFoundException(String message) { super(message); } }

Refatore o controlador:

@GetMapping("/{id}") public Tarefa buscarPorId(@PathVariable Long id) { // Código limpo! Focado na regra de negócio. return repository.findById(id) .orElseThrow(() -> new ResourceNotFoundException("ID não encontrado")); }

🔹 Por estender RuntimeException, ela é uma exceção não verificada (unchecked): não precisa de throws na assinatura nem de try/catch em quem chama.

🔹 O nome diz o que aconteceu ("recurso não encontrado") em vez de um genérico "Não encontrado!". É esse tipo que o tratamento centralizado do próximo card vai reconhecer.

⚠ Sozinha, a exceção ainda vira 500: para o Spring, ela é uma RuntimeException como outra qualquer. Quem a traduz para 404 é o @ControllerAdvice.
🛡 Centralize o Tratamento com @ControllerAdvice Aula 09 GlobalExceptionHandler

🔹 @ControllerAdvice: é uma classe que "escuta" exceções de todos os controladores.

🔹 Usamos @ExceptionHandler dentro dela para tratar exceções específicas. O código do slide:

@ControllerAdvice public class GlobalExceptionHandler { // Captura nossa exceção customizada @ExceptionHandler(ResourceNotFoundException.class) public ResponseEntity<String> handleNotFound(ResourceNotFoundException ex) { // E a traduz para um 404 return ResponseEntity.status(HttpStatus.NOT_FOUND) .body(ex.getMessage()); } }
HTTP/1.1 404 Not Found Content-Type: text/plain;charset=UTF-8 ID não encontrado

🔹 No Task Manager: o ErrorResponse. Uma String solta não diz o status, a rota nem o momento do erro. O planejamento da aula 09 pede um corpo de erro próprio, igual para todos os erros da API:

public class ErrorResponse { private LocalDateTime timestamp; private int status; private String erro; private String mensagem; private String caminho; // construtor (status, erro, mensagem, caminho) com timestamp = LocalDateTime.now() + getters } @ExceptionHandler(ResourceNotFoundException.class) public ResponseEntity<ErrorResponse> handleNotFound(ResourceNotFoundException ex, HttpServletRequest request) { ErrorResponse erro = new ErrorResponse(404, "Não encontrado", ex.getMessage(), request.getRequestURI()); return ResponseEntity.status(HttpStatus.NOT_FOUND).body(erro); } @ExceptionHandler(MethodArgumentNotValidException.class) // lançada pelo @Valid public ResponseEntity<ErrorResponse> handleValidacao(MethodArgumentNotValidException ex, HttpServletRequest request) { String mensagem = ex.getBindingResult().getFieldErrors().stream() .map(e -> e.getField() + ": " + e.getDefaultMessage()) .collect(Collectors.joining("; ")); ErrorResponse erro = new ErrorResponse(400, "Dados inválidos", mensagem, request.getRequestURI()); return ResponseEntity.badRequest().body(erro); }
HTTP/1.1 404 Not Found Content-Type: application/json { "timestamp": "2026-11-24T19:12:30.481", "status": 404, "erro": "Não encontrado", "mensagem": "Tarefa com id 99 não encontrada", "caminho": "/api/v1/tarefas/99" }
💡 O 400 da aula 08 finalmente explica o erro: "mensagem": "titulo: O título deve ter no mínimo 3 caracteres; prioridade: A prioridade é obrigatória". Imports: org.springframework.web.bind.annotation.ControllerAdvice/ExceptionHandler, org.springframework.web.bind.MethodArgumentNotValidException e jakarta.servlet.http.HttpServletRequest.
🧪 O Problema: "Contaminação" do Controlador Aula 09

Por que tanto trabalho, se o .map(...).orElse(...) da aula 08 já devolvia 404? Porque o controlador está fazendo duas coisas: lógica de negócio e lógica de resposta HTTP.

@GetMapping("/{id}") public ResponseEntity<Tarefa> buscarPorId(@PathVariable Long id) { return repository.findById(id) .map(t -> ResponseEntity.ok(t)) // Lógica de resposta HTTP .orElse(ResponseEntity.notFound().build()); // Lógica de erro }

🔹 Objetivo: queremos que o controlador apenas execute a lógica e lance uma exceção se algo der errado. Quem decide o status e o corpo do erro é o GlobalExceptionHandler, em um lugar só.

📨 DTOs (Data Transfer Objects) Aula 10 Contrato da API

🔹 É um POJO (classe Java simples).
🔹 NÃO é uma entidade (não tem @Entity).
🔹 É um "contêiner" de dados feito sob medida para sua API.
🔹 Você define exatamente quais campos o cliente pode ver e quais pode enviar.
🔹 Contrato da API: seu DTO. Persistência: sua Entidade.

Entidade (Banco) vs. DTO (API): o exemplo do slide é quase igual ao Usuario do Task Manager.

Usuario.java (@Entity)UsuarioDTO.java (POJO)
@Id private Long id;private Long id;
private String nome;private String nome;
private String email;private String email;
private String senha; // Sensível// Sem senha!
private List<Tarefa> tarefas; // Interno// Sem tarefas

🔹 No slide, o campo interno é dataCadastro. No Task Manager, o que fica de fora é a lista tarefas, que causaria a recursão infinita Usuario → tarefas → usuario → ... no JSON.

🔹 O TarefaDTO segue o fluxo do slide da aula 10: o mesmo DTO entra validado no POST/PUT e sai no GET. O usuário vira só o usuarioId:

package br.org.irede.taskmanagerapi.dto; public class TarefaDTO { private Long id; @NotBlank(message = "O título é obrigatório") @Size(min = 3, message = "O título deve ter no mínimo 3 caracteres") private String titulo; private String descricao; @NotNull(message = "A prioridade é obrigatória") private Prioridade prioridade; private LocalDate prazo; private boolean concluida; @NotNull(message = "O usuário é obrigatório") private Long usuarioId; // getters e setters (Alt+Insert no NetBeans) }
📌 As validações saem da entidade e vão para o DTO: é ele que recebe o JSON. Com o DTO na fronteira, o @JsonIgnore de Tarefa.usuario e de Etiqueta.tarefas deixa de ser necessário, porque a entidade nunca mais é serializada.
✍ Mapeamento Manual Aula 10

Escrevemos o código de conversão na mão. O exemplo do slide (Cliente → ClienteDTO), no Task Manager:

private UsuarioDTO converterParaDto(Usuario usuario) { UsuarioDTO dto = new UsuarioDTO(); dto.setId(usuario.getId()); dto.setNome(usuario.getNome()); dto.setEmail(usuario.getEmail()); return dto; } private TarefaDTO converterParaDto(Tarefa tarefa) { TarefaDTO dto = new TarefaDTO(); dto.setId(tarefa.getId()); dto.setTitulo(tarefa.getTitulo()); dto.setDescricao(tarefa.getDescricao()); dto.setPrioridade(tarefa.getPrioridade()); dto.setPrazo(tarefa.getPrazo()); dto.setConcluida(tarefa.isConcluida()); dto.setUsuarioId(tarefa.getUsuario().getId()); // só o id do dono return dto; }

🔹 Vantagem: tudo explícito, fácil de ler e de depurar. Desvantagem: uma linha por campo, e um campo novo na entidade exige lembrar de atualizar a conversão.

🔹 tarefa.getUsuario().getId() não dispara SELECT: com Tarefa.usuario LAZY, o Hibernate já guarda o id do dono no proxy.

🤖 Mapeamento Automático (ModelMapper) Aula 10 no projeto: aula 11

🔹 Usamos uma biblioteca para fazer o trabalho pesado.
🔹 Princípio: ele "lê" os nomes dos atributos e copia os valores se os nomes forem iguais (nome -> nome).

🔹 Dependência (pom.xml):

<dependency> <groupId>org.modelmapper</groupId> <artifactId>modelmapper</artifactId> <version>3.2.0</version> <!-- o Spring Boot não gerencia esta versão --> </dependency>

🔹 Configurando o ModelMapper (Obrigatório!). Precisamos "ensinar" o Spring a criar e gerenciar o ModelMapper: criamos uma classe de configuração com a anotação @Bean.

@Configuration public class AppConfig { @Bean public ModelMapper modelMapper() { return new ModelMapper(); } }

🔹 Usando o ModelMapper (é simples!). Injetamos o ModelMapper em nossa classe de serviço e usamos o método .map():

@Autowired private ModelMapper modelMapper; // Injeta o bean @Autowired private TarefaRepository repository; public TarefaDTO buscarPorId(Long id) { Tarefa tarefa = repository.findById(id).orElseThrow(); // Mapeamento automático! return modelMapper.map(tarefa, TarefaDTO.class); }

🔹 titulo → titulo, prazo → prazo... e até usuario.id → usuarioId: o ModelMapper quebra usuarioId em "usuario" + "id" e encontra getUsuario().getId().

📅 No Task Manager, o ModelMapper e a classe de serviço entram na aula 11 (assunto 06). Na aula 10 fazemos a conversão manual, para entender o que a biblioteca automatiza. O AppConfig vai para o pacote config.
🏛 Integração com Banco via JPA e Separação de Camadas Aula 10 3 camadas

Agora que temos DTOs e uma forma de mapeá-los, onde essa conversão deve acontecer? A resposta é: na Camada de Serviço (Service Layer). A arquitetura padrão de uma API Spring Boot é dividida em três camadas:

AnotaçãoCamadaNo Task Manager
@RestControllerApresentaçãoTarefaController: HTTP, status, DTOs
@ServiceServiço / NegócioTarefaService (aula 11): regras e conversão
@RepositoryAcesso a DadosTarefaRepository: JPA

Boas práticas: um projeto profissional é organizado por responsabilidade.

br.org.irede.taskmanagerapi/ ├── controller/ (APIs, HTTP) ├── service/ (Lógica de Negócio) ├── repository/ (Acesso ao Banco) ├── model/ (Entidades @Entity) ├── dto/ (Classes de Transferência) └── config/ (Beans, Segurança)

Pense na Camada de Serviço como o núcleo protegido da sua aplicação:

Fluxo de Entrada (POST): JSON → Controller → TarefaDTO (Validado) → Fronteira (Service) → Tarefa (Entity) → Repository → Banco Fluxo de Saída (GET): Banco → Repository → Tarefa (Entity) → Fronteira (Service) → TarefaDTO → Controller → JSON

🔹 O Controlador e o Cliente Externo nunca tocam na Entidade.

📅 Na aula 10, sem a camada de serviço, a conversão fica em métodos privados do controlador: o cliente externo já não vê a entidade. Na aula 11, os converterParaDto e o acesso ao repositório se mudam para o TarefaService, e aí o controlador também deixa de tocar na entidade. 🚀 Curiosidades sobre Status HTTP, Erros e DTOs
🫖
418 I'm a teapot
O código 418 nasceu de uma piada de 1º de abril: a RFC 2324 (1998) definiu o protocolo HTCPCP, para controlar cafeteiras, e um bule de chá que recebe um pedido de café responde "I'm a teapot". O código nunca virou parte do HTTP, mas a RFC 9110 o deixou reservado justamente porque muita gente o implementou de brincadeira.
🔐
401 "Unauthorized" quer dizer "não autenticado"
O nome é histórico e confunde: o 401 significa que faltam credenciais válidas (quem é você?), e a especificação exige que a resposta traga o cabeçalho WWW-Authenticate. Falta de permissão (sei quem você é, mas não pode) é o 403 Forbidden. Os dois voltam na aula 14, com JWT.
📚
DTO é um padrão catalogado
O Data Transfer Object está no livro Patterns of Enterprise Application Architecture, de Martin Fowler (2002). A motivação original era juntar vários dados em um único objeto para economizar chamadas remotas. Hoje o uso mais comum é o do slide: definir o contrato da API, separado da entidade.
🧾
De onde vem o JSON de erro padrão do Spring Boot
Aquele corpo com timestamp, status, error e path é montado pelo BasicErrorController, que o Spring Boot registra no caminho /error. Quando uma exceção não é tratada, o servidor encaminha a requisição para lá. Com o @ControllerAdvice, a exceção é resolvida antes e esse corpo padrão não aparece.
📜
Existe uma RFC para corpo de erro
A RFC 9457 (2023, substituta da RFC 7807) define o formato Problem Details (application/problem+json), com campos como type, title, status e detail. O Spring 6 traz a classe ProblemDetail para isso. No Task Manager usamos um ErrorResponse próprio, como pede o planejamento: a ideia é a mesma, um corpo de erro padronizado.
🕰
@ControllerAdvice e @RestControllerAdvice
O @ControllerAdvice chegou no Spring 3.2 (2012). O @RestControllerAdvice, do Spring 4.3, é só um atalho: @ControllerAdvice + @ResponseBody. Como nossos handlers devolvem ResponseEntity, que já é escrita no corpo da resposta, os dois funcionam igual aqui.
